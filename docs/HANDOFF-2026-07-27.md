## 2. Resend 메일 연동 (C) — 진행 상황

### 2-1. 왜 Resend 인가 (자체 SMTP 서버 검토 결과)

사용자가 "Postfix/Sendmail 로 직접 구축하면 되지 않나" 를 제기했고, **실측으로 불가 확인**:

```
아웃바운드 :25  → naver/gmail/samsung MX 전부 타임아웃 (OCI 기본 차단)
아웃바운드 :587 → Resend/SES/Gmail 전부 열림
158.180.79.39 의 PTR → 없음 (OCI 표준 인스턴스는 커스텀 PTR 불가)
```

25번이 막혀 자체 MTA 는 **한 통도 못 보낸다**. 뚫려도 PTR 부재·클라우드 IP 평판·도메인 이력 0
세 문제가 남고, 수신처가 `@samsung.com` 같은 기업 게이트웨이라 조용히 스팸 처리된다.
**Listmonk 도 대안이 아니다** — 뉴스레터 관리자일 뿐 배달은 외부 SMTP 에 의존한다(우리 `mailer.py` 와 같은 층).

### 2-2. 완료된 것

**DNS (가비아, `jobcho.wiki`)** — 3레코드 전부 전파 확인:

| 타입 | 호스트 | 값 | 검증 |
|---|---|---|---|
| MX | `send` | `10 feedback-smtp.ap-northeast-1.amazonses.com.` | ✅ |
| TXT | `send` | `v=spf1 include:amazonses.com ~all` | ✅ |
| TXT | `resend._domainkey` | `p=MIGf...` | ✅ 216자·base64→162바이트 DER·끝 `QAB` **잘림 없음** |

**`server/.env`** (gitignore·`ubuntu:ubuntu 600`) — 자격증명 주입 완료, **모드는 아직 `console`**:

```
MAILER_MODE=console        ← Verify 통과 후 smtp 로 바꾼다
SMTP_HOST=smtp.resend.com
SMTP_PORT=587
SMTP_USER=resend
SMTP_FROM="loupit <no-reply@jobcho.wiki>"   ← 따옴표 필수(§2-4 ①)
SMTP_PASS=re_...
```

**키 유효성 실측**: TCP 연결 0.7s → STARTTLS 인증서 검증 통과 → `AUTH` 성공.
발송만 `550 The jobcho.wiki domain is not verified` — **대시보드 Verify 미클릭 때문**.

### 2-3. 코드 하드닝 — 결함 7건 수정 (`a872d68` + `6e2a6bc`)

`mailer_mode=smtp` 경로는 **저장소 역사상 한 번도 실행된 적이 없었다**(줄곧 ConsoleMailer).
실투입 직전 점검 + 적대적 검토(50 에이전트·5 렌즈, `wf_ebae8f5a`)로 잡은 것들:

| # | 결함 | 수정 |
|---|---|---|
| 1 | `starttls()` 기본 컨텍스트가 `check_hostname=False`·`CERT_NONE` — 암호화만 되고 **상대 미확인**(MITM 시 SMTP 비밀번호·인증코드 노출) | `ssl.create_default_context()` 명시 |
| 2 | `socket.getdefaulttimeout()=None` → 무한 블록 → `to_thread` 스레드풀 영구 점유 → API 전체 정지 | `timeout=8s` |
| 3 | 발송 실패가 500 으로 새어 "균일 204"(계정 열거 차단) 계약 파괴 | `auth_code.send_code_safe` 가 삼키고 **예외 타입명만** 로깅(제공자가 주소·코드를 반향하는 경우 대비) |
| 4 | `smtp_from or smtp_user` 폴백 — Resend 의 user 는 리터럴 `"resend"`(주소 아님) → From 무효 | `resolve_sender()` 가 **최종값**에 `@` 검사(폴백 자체는 유지 — Gmail 식 정당) |
| 5 | **[blocker]** ③의 삼킴이 ④의 fail-closed `RuntimeError` 까지 삼킴 → 오설정이 "기동 성공+204+메일 0통" | 검증을 **기동 시점**으로 이동(`main.validate_mail_config`, lifespan) |
| 6 | **[blocker]** 릴리스 게이트가 실제 메일 발송 — `test_csrf.py:73` 이 CSRF 헤더 붙여 login-code 호출·204 검증 = 핸들러 완주 | conftest 가 `MAILER_MODE=console` **덮어쓰기**(setdefault 아님) |
| 7 | `mailer_mode` 값 미검증 — `SMTP`·`stmp`·`smtp `(공백)가 조용히 ConsoleMailer 로 폴백 | 리터럴 집합 검증 |

> **⑤가 이 세션 최대 교훈**: 같은 커밋의 수정 ③과 ④가 서로를 무력화했다. 5개 렌즈 중 4개가
> 독립적으로 같은 결함에 수렴했다. **설정 오류와 일시적 발송 실패는 다른 종류다** — 전자는
> 배포에서 크게 죽어야 하고 후자만 삼켜야 한다.

**신규 테스트**: `test_mailer_smtp_hardening.py`(8) · `test_mail_config_gate.py`(11) — 전부 무 DB·무 네트워크

**① `SMTP_FROM` 은 반드시 따옴표로 감쌀 것**

## 3. 재개 절차 — 여기부터 이어서 하면 된다

### 3-A. 레이트리밋 배선 (**실메일 전환 전 필수 · DNS 와 독립**)

**남은 유일한 blocker.** 지금 SMTP 를 켜면 무료 티어가 20초에 소진되고 도메인 평판이 망가진다.

실측 근거:
```
SPEC/11 이 loupit_mail 존을 13회 언급  →  /etc/nginx 전체에 0건 (명세만 있고 미배선)
beta vhost /api/v1/ 블록             →  limit_req 자체가 0건
정의된 존                            →  loupit_api 300r/m · loupit_log 20r/m 뿐
```

공격 경로: `POST /members/login-code` 는 세션 불필요, `require_csrf` 는 공개 상수 헤더의 **존재만**
검사(`deps.py:22-24`), 쿨다운은 이메일 해시 스코프라 **주소를 바꾸면 안 걸린다**
(`auth_code.py` `recent_unconsumed_exists`). → 단일 IP 로 분당 300통.

할 일:
1. `infra/nginx/loupit-limits.conf` 에 `loupit_mail` 존 신설(SPEC/11 §3.4 = 3r/m)
2. `loupit.conf`·`loupit-beta.conf` 에 `location = /api/v1/members/login-code`,
   `= /api/v1/employment/verify-code` 블록 추가 + `limit_req zone=loupit_mail`
3. beta `/api/v1/` 에 기본 `limit_req zone=loupit_api` 도 추가(현재 전무)
4. `nginx -t` → `systemctl reload nginx`
5. 롤백 = conf 백업 복원(`.bak-<날짜>`)

⚠ **라이브 nginx 수정이라 사용자 승인 필요.**

### 3-B. Resend Verify 후 전환

사용자가 대시보드에서 `Verify DNS Records` 를 누른 뒤:

1. **발송 확인**(앱 무관) — 전용 검증기가 저장소에 있다:
   ```
   python3 infra/deploy/verify_mail.py                 # 설정·연결·인증까지(발송 없음)
   python3 infra/deploy/verify_mail.py <수신주소>       # 위 + 실제 1통 발송
   ```
   단계별 검증: 설정 로드 → fail-closed → TCP → **인증서 검증 TLS** → AUTH → 발송.
   어느 단계에서 막히는지 바로 나오므로 "코드가 안 와요"를 추측으로 디버깅하지 않는다.
   비밀번호는 길이만 출력한다.

2. `server/.env` 의 `MAILER_MODE=console` → `smtp` (**한 줄만**)
   - 소유권 확인: `ubuntu:ubuntu 600` 유지되어야 함. 깨졌으면
     `sudo chown ubuntu:ubuntu server/.env && sudo chmod 600 server/.env`

3. `sudo systemctl restart loupit-beta-api` → 기동 성공해야 함
   - 실패하면 `validate_mail_config` 가 설정 오류를 잡은 것이다(의도된 fail-closed). 로그 확인.

4. **베타 로그인 e2e**: `https://beta.loupit.co/login` → 코드가 **메일로** 오는지
   (더 이상 `journalctl | grep ConsoleMailer` 에 안 나와야 정상)

5. **기업 게이트웨이 확인** — `@samsung.com` 등 실제 회사 도메인 수신 테스트.
   개인 메일(gmail/naver)은 통과해도 기업 게이트웨이에서 막히는 게 실제 위험이다.

### 3-C. journald 평문 코드 정리 (선택)

실측: `journalctl -u loupit-beta-api | grep -c ConsoleMailer` = **15건**.
수신 이메일 + 6자리 코드가 평문. `/var/log/journal` 은 **PERSISTENT**(2.8G).
`adm` 그룹(`ubuntu`·`bob`·`bread`·`syslog`)이 sudo 없이 읽는다 — `bob`(uid 1003)으로 15건 읽힘 실측.

**실피해는 낮다** — 7/23~25 베타 기록, 5분 TTL 이라 전부 만료, 주소도 운영자 본인 테스트용.
**구조가 문제다**: M9 ON + console 이면 앞으로도 계속 쌓인다. → §3-B 2번(SMTP 전환)으로 자동 해소.
기존 15건 삭제 여부는 사용자 결정(저널 vacuum 은 다른 로그도 지우므로 신중히).
