## 3. SUSPECT 1건 — `welfare_fund` 신규 코드

**원문은 「사내 근로복지기금 운영」까지만 말하고 대출·대부·융자를 한 글자도 쓰지 않는다.** 내가 원문에서 직접 확인했다.

내가 코퍼스를 직접 재검증한 결과:

| 기존 코드 | 회사 | 실제 문안 |
|---|---|---|
| `welfare_fund_loan` | 삼성화재 | BENEFIT_NM 「사내 근로복지기금 **대출**」 / QUAL 「생활안정 지원 항목의 사내 근로복지기금 **대출** (공식 페이지 — 대출 한도·이율·용도 미기재)」 |
| `welfare_fund_loan` | 현대건설 | BENEFIT_NM 「사내근로복지기금 **대출**」 / QUAL 「사내근로복지기금 운영, 복지기금 **대출** 지원(용도·한도 미공개)」 |

**수집기의 결론은 맞다** — 기존 2행 모두 대출을 명시한다. `welfare_fund_loan` 으로 넣으면 **원문에 없는 대출 제도를 코드로 단언**하게 되고, 이는 규칙 2·어휘 오염에 정면으로 걸린다.

그러나 판정을 SUSPECT 로 두는 이유는 반대쪽 비용이다. `welfare_fund` 는 **1사 전용 비교축**이 된다 — 웨이브 2에서 걸린 「뜻 없는 축(`disability_veteran`)」과 같은 형태다. 게다가 원문이 기금의 **혜택 내용을 전혀 밝히지 않아**(대상·한도·용도 전부 미기재), 규칙 5 의 신규 코드 조건 「원문이 혜택 내용을 밝힐 때만」을 엄밀히는 충족하지 못한다.

**내 권고: 유지.** 근거 — ① 파이프라인 안전성을 직접 확인했다. `generator/pages/heatmap.py:141` 의 `_item_labels` 가 `ITEM_LABEL.get(code) or 최빈 benefit_nm` 로 폴백하고, `server/tests/test_seed_integrity.py` 에 BENEFIT_CD 화이트리스트가 없다 → 신규 코드가 조용히 떨어지거나 빌드를 깨지 않는다. ② 반대로 `welfare_fund_loan` 으로 합치면 그 코드의 최빈 명칭이 3행 1:1:1 동률이 돼 **묶음 이름이 삽입 순서에 좌우된다**(대출 2 · 운영 1). ③ 뜻을 지키는 쪽이 비교의 거짓을 만들지 않는다.

**감사에게**: 축 통합은 이 회사 한 곳이 아니라 `welfare_fund*` 전체를 놓고 전역으로 결정할 일이다. 통합을 택하면 SQL 의 `'welfare_fund'` 한 곳만 바꾸면 되고 행 수·SORT 는 불변이다.

| **「기본급 + 보너스(600%) + α(성과급)」** (`welfare-contents-wrap2` 「급여」 블록) | `bonus` · compensation · **AMT NULL** · QUAL 예: 「공식 채용 페이지 급여 항목의 연 보너스 600퍼센트와 성과급 (지급 시기·산정 기준 미기재)」 | 규칙 8-2 「급여성 수당은 복지가 아니다」 + 리드 지시 | **부분 타당 — MISSED 로 올린다.** 규칙 8-2 가 든 예시는 **수당**(학위·자격 수당·초임)이지 연 상여율이 아니다. 코퍼스에 **S-Oil `bonus` / 「상여금」 / AMT NULL / QUAL 「연 800% 상여금」** 이 이미 있다 — 동국제약 600% 와 모양이 같다. 빼면 `bonus` 축에서 동국제약만 비어 보인다 |

- **금액 칸에 600 을 절대 넣지 말 것.** 비율이다(현대제철 「본인 100%」→`100` 라이브 사고 유형, 정리 커밋 `eb4120c`).
- 행을 올리면 SORT 는 compensation 섹션 `50` 뒤 `51` 이 자연스럽다(`excellence_award` 와 같은 섹션).
- **리드가 「급여는 제외」를 명시적으로 지시했다면 그 결정이 우선한다.** 다만 그 경우 S-Oil 행도 같은 기준으로 재검토해야 코퍼스가 일관된다 — 이건 이 회사 한 곳의 문제가 아니라 전역 결정이다.

## 7. 근거표(evidence) 자체의 결함 — 행 판정과 별개

행 판정을 바꾸지는 않지만 기록으로 남긴다.

1. **S1 의 sha256 두 개가 모두 재현 불가.** 정본 HTML 에 요청마다 바뀌는 캐시버스터(`?v=<unix ts>`)가 박혀 있어 **페이지 해시가 매 요청 달라진다**(evidence `f294da53…` vs 내 `93da8d6b…`, 바이트 수는 18,674B 로 동일). `ul.welfare-ul` 블록 해시도 바이트 경계가 정의돼 있지 않아 재현되지 않았다(내 추출 `0242d7a2…`). **내용 자체는 수집기 사본과 바이트 동일함을 diff 로 직접 확인했으므로 근거의 실질은 성립한다.** 권고 — 이 사이트류는 페이지 해시 대신 **정규화한 항목 텍스트의 해시**를 남길 것(수집기가 이미 만든 `welfare-items.txt` 가 그 용도에 맞다).
2. **코퍼스 인용 1건이 실재하지 않는다.** evidence §3 이 삼성화재 행을 「사내 근로복지기금 대출, 출산 축하금, 경조사」로 인용했는데 **코퍼스에 그런 행이 없다.** 실제는 `welfare_fund_loan` 1행(「생활안정 지원 항목의 사내 근로복지기금 대출 …」)이고 「출산 축하금」은 별개의 `parenting` 행(삼성화재.sql:84)이다. **그 인용이 떠받치던 결론(기존 2행이 둘 다 대출을 명시한다)은 내가 독립 확인한 결과 참이다** — 결론은 살고 인용만 거짓이다. 근거표의 verbatim 인용은 실제로 읽은 문자열이어야 한다.
3. **숨김 확인 방법이 약했다.** evidence 는 「내려받은 페이지 전체에 `display:none` 0건」이라 적었는데, 숨김은 HTML 이 아니라 **CSS** 에 있다. 내가 `pc.css` 를 직접 받아 `.welfare*` 22블록을 검사해 0건임을 확인했으므로 **결론은 맞다.** 다음 웨이브에서는 외부 CSS 를 받아 확인할 것.

## 8. 수집기가 놓친 함정 (재수집·다음 웨이브로)

1. **캐시버스터가 박힌 사이트는 페이지 sha256 이 증거가 되지 않는다** — 매 요청 달라진다. 항목 텍스트를 정규화해 해시하라.
2. **숨김 검사는 HTML 이 아니라 외부 CSS 에서 한다** — 이번엔 결과가 같았지만 방법이 틀리면 다음엔 안 걸린다.
3. **근거표의 코퍼스 인용을 실제로 읽지 않고 적었다**(삼성화재 1건 허위 인용). 원문 인용이 근거표의 존재 이유다.
