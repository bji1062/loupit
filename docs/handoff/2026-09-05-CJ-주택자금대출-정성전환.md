# CJ 5개사 주택자금 대출 → 정성 항목 전환 (2026-09-05)

`TCOMPANY_BENEFIT.BENEFIT_AMT` 의 정의는 **연간 환산 금액(만원)**(`db/schema.sql`). 그런데 CJ 5개사의
`housing_loan` 행에는 **대출 원금 한도**가 들어 있었다. 원금은 연간 가치가 아니다. 다섯 행을 정성
항목으로 바꾸고 한도 사실은 설명으로 옮긴다. **사용자 결정(2026-09-05).**

## 왜

- 카드 힌트("숫자 = 연간 환산 금액")도 비교 계산(`web/assets/js/calc.js:192·317`)도 이 칸을 **연간
  가치로 합산**한다. 원금 한도가 섞이면 합계가 그만큼 허위가 된다.
- **CJ ENM 커머스부문 카드의 「등록 금액 합 1억 600만원」은 94% 가 이 한 행**(10000 = 1억)이었다.
- SPEC 07 **D-6**(금액 합계에 순위를 붙이지 않는다)은 이 문제를 **증상 쪽에서만** 눌렀다 — 원인 행은
  그대로 남아 카드·비교 리포트의 합계를 계속 부풀렸다. 이번에 원인 행 자체를 고친다.

## 무엇을 바꿨나 — 5행

| 회사(`COMP_ENG_NM`) | 전 | 후 |
|---|---|---|
| CJ ENM 커머스부문 `cj_enm_com` | 10000 · stated | NULL · none · 정성 |
| CJ CGV `cj_cgv` | 2000 · estimated | NULL · none · 정성 |
| CJ대한통운 `cj_logistics` | 2000 · estimated | NULL · none · 정성 |
| CJ올리브영 `cj_oliveyoung` | 2000 · estimated | NULL · none · 정성 |
| CJ제일제당 `cj_cheiljedang` | 2000 · estimated | NULL · none · 정성 |

`QUAL_YN=TRUE` · `BENEFIT_AMT=NULL` · `AMT_SOURCE_CD='none'` · `NOTE_CTNT=NULL`, 한도·무이자 사실은
`QUAL_DESC_CTNT` 로 보존한다(커머스 = "주택자금 최대 1억원 대출 지원 — 한도는 부문별로 다름(그룹 정본
2천만원)", 나머지 4사 = "무이자 2천만원 주택자금 대출 — 한도는 계열사별로 다름").
문체·컬럼 형태는 같은 그룹의 **기존 선례**를 그대로 따랐다: `CJENM엔터테인먼트부문.sql` ·
`CJ.sql` · `CJ프레시웨이.sql`.

**건드리지 않은 것**: 펄어비스 `housing_loan` 600 은 매월 50만원 = **진짜 연간 환산**이라 유지.
다른 회사의 `housing_loan` 도 대상이 아니다(대부분 이미 NULL).

## 적용 절차

```bash
# 1) 백업 — 파일명을 「되돌리기」 절에 그대로 적어 둘 것
mysqldump ... LOUPIT TCOMPANY_BENEFIT > ~/loupit-pre-cj-housing-loan-<날짜시각>.sql

# 2) 적용 전 확인 — 5행이 official 인지 눈으로 본다(verified 가 섞여 있으면 멈추고 판단)
mysql -h <host> -u <user> -p LOUPIT -e "
  SELECT c.COMP_ENG_NM, b.BENEFIT_AMT, b.AMT_SOURCE_CD, b.QUAL_YN, b.BADGE_CD
    FROM TCOMPANY_BENEFIT b JOIN TCOMPANY c ON c.COMP_ID = b.COMP_ID
   WHERE b.BENEFIT_CD = 'housing_loan'
     AND c.COMP_ENG_NM IN ('cj_cgv','cj_enm_com','cj_logistics','cj_oliveyoung','cj_cheiljedang');"

# 3) 마이그레이션 — -vv 로 문마다 Rows matched 를 찍는다(기대: 5문 x 1행)
mysql -vv -h <host> -u <user> -p LOUPIT < db/migrations/20260905_cj_housing_loan_to_qual.sql

# 4) 그 다음에 load.py 재적용 · 정적 재생성 · 배포
```

⚠ **`-vv` 없이는 0행이어도 조용히 성공한다.** 회사명이 틀려 `SET @c = (SELECT ...)` 가 NULL 이 되면
`UPDATE` 는 오류 없이 0행으로 끝난다. 합계 5행을 확인하지 못하면 적용됐는지 알 수 없다.

⚠ **실행 순서는 무관하다 — 마이그레이션과 `load.py` 중 무엇이 먼저든 종착 상태는 같다.**
`TCOMPANY_BENEFIT` 시드는 `INSERT IGNORE` 가 아니라 `INSERT ... ON DUPLICATE KEY UPDATE`(**업서트**)다
(`INSERT IGNORE` 는 `TCOMPANY` 회사 행에만 쓰인다). 그래서 마이그레이션을 건너뛰고 고친 시드로
`load.py` 를 재적용(`--fresh` 아님)해도 같은 5행이 그대로 바뀐다 — loupit_test 실측으로 확인했고
백필 집계도 `--fresh` 와 동일했다(stated 75 · estimated 556 · none 1124).
마이그레이션을 남기는 이유는 순서가 아니라 **서빙 DB 변경을 명시적·감사 가능한 파일로 남기는 관례**다.

⚠ **뒤집힌 함의 — 시드 수정은 재적용 한 번에 곧장 서빙 행을 덮는다.** 같은 키
(`COMP_ID` + `BENEFIT_CD`)라면 **재직자가 고친 행(`BADGE_CD='verified'`)도 시드 값으로 되돌아간다.**
마이그레이션에는 `BADGE_CD = 'official'` 가드를 넣어 두었지만, 그 가드는 이 마이그레이션만 지킬 뿐
**재적용까지 막지는 못한다.** 재적용 정책 차원의 미해결 문제로 기록해 둔다(이번 변경 범위 밖).

⚠ 회사 페이지는 정적이다 — 마이그레이션 뒤 **정적 재생성**을 해야 카드 숫자가 바뀐다.

## 검증 (loupit_test 실측, 프로덕션 무접촉)

1. 수정 전 시드로 `--fresh` → 6행 스냅샷: 커머스 10000/stated, 4사 2000/estimated, 펄어비스 600/stated.
2. 마이그레이션 적용 → **5행 변경**(`mysql -vv` 로 UPDATE 5개가 각 `Rows matched: 1  Changed: 1`).
3. **재적용 → 0행**(`WHERE ... QUAL_YN = FALSE` 덕분에 멱등).
4. SB-3 불변식(`QUAL_YN=TRUE ⇒ 금액 NULL & amt_source='none'`) 위반 **0**, 총행 **1755** 불변(SD-4).
5. 펄어비스 · CJ ENM 엔터 · CJ · CJ프레시웨이 행 **불변**.
6. **수정한 시드로 `--fresh` → 5행이 마이그레이션 결과와 필드 단위로 완전 일치**
   (`BENEFIT_AMT`·`AMT_SOURCE_CD`·`QUAL_YN`·`NOTE_CTNT`·`QUAL_DESC_CTNT`·`BENEFIT_NM`·`BADGE_CD`·`SORT_ORDER_NO`).
7. **BADGE_CD 가드 실증**: `cj_cgv` 행을 재직자 수정으로 흉내 낸 뒤
   (`BADGE_CD='verified'`, 금액 1200) 마이그레이션 적용 → **`Rows matched: 0` 으로 건너뛰고 행이 그대로**
   보존된다. 가드가 없던 판본에서는 같은 행이 조용히 `NULL`·`none` 으로 덮였다.
8. **경로 동치(전수)**: 「마이그레이션 적용」 종착 상태와 「고친 시드 `--fresh`」 종착 상태를
   `TCOMPANY_BENEFIT` **전체 1755행 체크섬**으로 비교 → **완전 일치**(`3760812593711`).
   순서가 무관하다는 위 서술의 근거다.
9. **되돌리기 SQL 실증**: 「되돌리기」 절의 역방향 UPDATE 5문을 적용 → `Rows matched: 1` x 5,
   `housing_loan` 61행이 **변경 전 스냅샷과 필드 단위로 완전 일치**.
10. 백필 집계 이동: `stated 76→75` · `estimated 560→556` · `none 1119→1124`(합 0) — **다른 행으로 번진
   변화 없음**. `anchor_demoted 57→53` 은 사라진 CJ 2000 앵커 4건 그대로다.
11. 테스트: 시드 25 · generator 462 · node 854 전부 초록. **SB-7 표본은 손대지 않았다** — CJ stated
   표본은 `cj welfare_point`(앵커 강등 확인)이고 stated 브랜치는 "고유 stated 행 ≥1" 이라 이번 변경과
   무관하다.

## 되돌리기

**좁은 경로(권장) — 5행만 역방향 UPDATE.** 전체 테이블 복원과 달리 다른 행을 건드리지 않는다.

```sql
-- CJ ENM 커머스부문
SET @c = (SELECT COMP_ID FROM TCOMPANY WHERE COMP_ENG_NM = 'cj_enm_com');
UPDATE TCOMPANY_BENEFIT
   SET BENEFIT_AMT = 10000, AMT_SOURCE_CD = 'stated', QUAL_YN = FALSE,
       NOTE_CTNT = '주택자금 최대 1억원 대출 지원 (그룹 정본 2천만원 대비 상향)',
       QUAL_DESC_CTNT = NULL
 WHERE COMP_ID = @c AND BENEFIT_CD = 'housing_loan' AND BADGE_CD = 'official';

-- CJ CGV · CJ대한통운 · CJ올리브영 · CJ제일제당 (네 회사 값이 같다 — eng_nm 만 바꿔 4번)
SET @c = (SELECT COMP_ID FROM TCOMPANY WHERE COMP_ENG_NM = 'cj_cgv');   -- cj_logistics / cj_oliveyoung / cj_cheiljedang
UPDATE TCOMPANY_BENEFIT
   SET BENEFIT_AMT = 2000, AMT_SOURCE_CD = 'estimated', QUAL_YN = FALSE,
       NOTE_CTNT = '무이자 2천만원 주택자금 대출 (한도는 계열사별로 다름)',
       QUAL_DESC_CTNT = NULL
 WHERE COMP_ID = @c AND BENEFIT_CD = 'housing_loan' AND BADGE_CD = 'official';
```

**더 좁은 경로 — 시드 revert + 재적용.** 시드가 업서트라서(위 「적용 절차」 참고) 시드 5파일을
`git revert` 한 뒤 `load.py` 를 재적용하면 같은 5행이 원래 값으로 돌아온다. 역방향 SQL 을 손으로
쓰지 않아도 되고, 백필 집계(`stated 76 · estimated 560 · none 1119`)까지 함께 복원된다.

**전체 덤프 복원 — 최후 수단.** `/root/loupit-benefit-pre-cj-loan-qual-20260905101111.sql (TCOMPANY_BENEFIT 1,755행 · 적용 전 6행 스냅샷 /root/loupit-cj-loan-rows-pre-20260905101111.tsv)`
(적용 담당자가 실제 파일명을 여기 적을 것. **비워 두면 되돌리기 대상이 특정되지 않는다**).
⚠ 이 경로는 `TCOMPANY_BENEFIT` **전체**를 백업 시점으로 되돌린다 — 그 사이에 들어온
**재직자 등록·수정 등 다른 변경까지 함께 사라진다.** 위 두 경로로 충분하면 쓰지 마라.

어느 경로든 되돌린 뒤에는 **시드 5파일도 함께 revert** 해야 다음 재적용·`--fresh` 가 되살리지 않는다.
