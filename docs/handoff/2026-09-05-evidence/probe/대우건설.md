## 결론

공식 출처 기반 복지 수집 **불가**. 사유는 콘텐츠 부재가 아니라 **robots** 다 — 복리후생 페이지는 분명히 존재하는데(`erecruit.daewooenc.com/rem/apply/recruit/apply_benefit.jsp`), 그 호스트가 전 크롤러를 `Disallow: /` 로 막는다. 허용된 두 호스트(본사·신입공채)에는 복지 항목이 **0개**라 대체 경로가 없다.

재시도 조건은 둘 중 하나다.
1. `erecruit` 의 robots.txt 가 완화될 때(현재 26바이트 전면 차단), 또는
2. 본사 `www.daewooenc.com` 이나 `recruit.daewooenc.com` 에 복리후생 페이지가 신설될 때. 후자는 `menu1_3.jsp` 라는 자리가 이미 있어 캠페인 개편 시 살아날 여지가 있다.

## 수집 설계 시 유의

1. **robots 는 호스트 단위로 다시 읽어라.** `www` 가 허용이라고 `erecruit` 를 허용으로 넘기면 명시적 전면 차단을 위반한다. 도메인이 같아도 서브도메인마다 robots 가 갈리는 실제 사례다.
2. **한국어 소프트 거부를 차단 사전에 넣어라.** `잘못된 페이지 접근입니다` 는 200/209B 로 오고 영문 deny 키워드에 걸리지 않는다. 본문 2KB 미만 규칙과 한국어 거부 문구를 함께 걸어야 한다.
3. **HTML 주석을 먼저 걷어내라.** 이 회사는 `<!-- 복지제도 -->` 라는 빈 주석만 남아 있어, 주석을 세는 파서라면 「복지 섹션 있음」으로 오탐한다. 항목은 0이다.
4. **`sitemap.xml` 200 을 신뢰하지 마라.** 본사 사이트는 XML 대신 홈페이지 HTML 을 200 으로 돌려준다. `<loc>` 존재 여부로 검증할 것.
5. **재시도 감시 대상은 `erecruit.daewooenc.com/robots.txt` 26바이트 하나**다. 이 파일만 주기적으로 확인하면 되고, 그 전까지는 본문 요청을 보내지 않는다.
