# 에이전트 편집 도구가 `\u0000` 같은 이스케이프를 **실제 바이트**로 써 넣는다 — 파일이 조용히 바이너리가 된다

**발견**: 2026-08-27 레인 B — `login.js` 의 `safeNext` 에 제어문자 거부 정규식 `/[\s\u0000-\u001f\u007f]/` 를 Edit 도구로 넣은 뒤.
**증상**: `grep -n safeNext web/assets/js/login.js` 가 **아무것도 출력하지 않는다**(exit 1). `wc -l` 은 정상. 이어서 같은 줄을 다시 Edit 하려니 "String to replace not found".

## 무엇이 잘못됐나

편집 도구의 문자열 인자가 JSON 으로 직렬화되면서 `\u0000`·`\u001f`·`\u007f` 가 **이스케이프 문자열이 아니라
그 코드포인트 자체**(NUL·US·DEL 바이트)로 파일에 기록됐다. 소스는 겉보기엔 멀쩡하지만:

- GNU grep 은 NUL 이 든 파일을 바이너리로 보고 매치 줄을 **출력하지 않는다**(메시지는 stderr 로만) —
  "함수가 없다"로 오독하기 딱 좋다.
- Node 는 정규식 클래스 안의 실제 NUL 을 그대로 받아들여 **테스트는 통과한다**. 즉 아무도 못 알아챈다.
- 같은 이유로 Bash 도구에 `\n`·`\u0000` 이 든 heredoc 을 넣으면 "control characters" 로 거부된다 —
  거부되는 쪽은 안전하고, **거부되지 않고 쓰이는 쪽이 위험**하다.

## 교훈

- 소스에 유니코드/제어문자 이스케이프를 넣을 땐 편집 후 **바이트 검사**를 한 번 하라:
  `python3 -c "b=open(p,'rb').read(); print([c for c in b if c<9 or 13<c<32])"` → `[]` 여야 한다.
  (이 저장소의 `pre-commit`·CI 에는 이런 가드가 없다 — 추가 후보.)
- `grep` 이 있어야 할 문자열에 침묵하면 "없다"가 아니라 **"바이너리다"** 를 먼저 의심하라 — `grep -a` 또는 `od -c` 로 확인.
- 복구는 python 으로 바이트 치환(`b"\x00-\x1f"` → `b"\\u0000-\\u001f"`) — 편집 도구로 다시 쓰면 같은 일이 반복된다.
