> **목적**: 회사 수 자체를 늘린다(102 → 1차 목표 ~150). 배경: 복지 재수집 3레인

## 1. 확정 제안

- **P-1. 등록 기준(강화된 INV-6)**: 다음 3축을 모두 갖춘 회사만 등록한다 —
  ①복지: 공식 1차 출처 실사 통과 + 3레인 수집·검증 완료(행 ≥8 권장)
  ②재무: DART corp_code 확정 + `dart_finance` 적재
  ③직원: `dart_employ` 적재. → thin page 원천 차단(신규 페이지가 기존 페이지 평균 두께 이상).
- **P-2. 1차 목표 +48 (102→150)**: GC-2 의 200 하드 가드 안쪽. 웨이브 **10~12개사** 단위
  (배치 1과 같은 규모 — 병렬 수집·검증·검수·핀 갱신이 한 호흡에 도는 크기).
- **P-3. 후보는 실사가 정한다**: 목록을 먼저 확정하지 않는다. 후보 풀(§2)에서 **실사 프로브**
  (공식 복지 소스 존재·robots 허용·접근성)를 통과한 회사만 수집 단계로 넘어간다.
  실측 통과율: 대형 6/6 · 코스닥 중소형 4/6 · 신규 후보 5/6 (2026-08-31, 18사).
- **P-4. 절차는 배치 1 정본 재사용**: 수집(Opus 5) → 적대검증(Fable 5) → 검수 → 반영.
  확립 규칙 그대로 — 법정 제도 미수록 · 구본 없음(신규라 오염 걱정 無) · 근거 인용 필수 ·
  금액은 명시값만(신규 회사는 앵커 승계 대상 자체가 없음 → est 배지 + 무금액 정성행 중심).

## 2. 후보 선정 — 유니버스 3,984 → 웨이브 큐

corpCode.xml 실측: 상장 법인 3,984 (2026-08-21). 필터 파이프라인:

```
상장 3,984
 → [F1] 기등록 102 제외
 → [F2] 규모·인지도 컷: KOSPI200 + KOSDAQ150 지수 편입 ∪ 시총 상위권      (~300)
 → [F3] 검색 수요 순위: 네이버 데이터랩 검색 트렌드로 "회사명+채용/연봉/복지"
        관심도 랭킹 (취업 관심 없는 회사 페이지는 유입 가치가 낮다)
 → [F4] 업종 균형: 기존 102 와 히트맵·관련회사 연결이 생기도록 업종 분산
        (1곳짜리 업종 남발 금지 — 관련회사 링크·트렌딩 폴백이 짝을 못 찾는다)
 → 웨이브 큐 (~150개 후보를 순위대로)
 → [F5] 웨이브마다 실사 프로브 12~15사 → 통과 10~12사만 수집 진입
```

- 그룹 계열사(삼성·현대·LG·SK·롯데·한화·CJ…)는 **회사명 매칭 사람 검수 필수**(오매핑
  전력 — bokziri 148건·CJ.sql·에코비트). corp_code 는 `corp_code_match.py` 의
  자동확정/REVIEW/MANUAL 절차 그대로.
- 금융사(은행·보험·증권·카드)는 등록 가능 — 지표 세트 분기가 이미 있다. 단
  `FINANCIAL_COMPANIES` 추가 + `FINANCIAL_7` 핀 갱신 필수(§3).
- 실사에서 확인된 즉시 후보: KB금융·LG이노텍·넷마블·루닛·더존비즈온 (2026-08-31 프로브
  통과). POSCO홀딩스는 robots 전면차단으로 **수집 불가** — 등록 기준 미달.

## 3. 회사 1개 등록 — 접점 정본 (2026-09-01 전수 탐색)

시드 SQL 하나로 페이지·사이트맵·REF 번들·GNB 검색은 **자동**이다. 자동이 아닌 것:

| # | 접점 | 안 하면 (조용한 실패 순위) |
|---|---|---|
| 1 | `db/seed/benefit/sql/<사명>.sql` — 자기등록 INSERT(정규식 형식 엄수) + `-- 출처:`/`-- URL:` 헤더 + 복지 ≥1행. **주석에 홑따옴표 금지** | 형식 어긋나면 시드 전체 실패(차라리 시끄러움). 출처 헤더 누락 → VERIFIED 가 2026-07-10 으로 굳어 만료 임박 배지 |
| 2 | `db/seed/company_meta.py` 별칭 override dict (CJ_AFFILIATE_ALIASES 패턴) | 🥇 **가장 조용한 실패** — 검색이 브랜드명으로 0건, 경고 로그뿐 |
| 3 | `db/seed/corp_code_map.csv` 1행 (+금융사면 `load_corp.py` FINANCIAL_COMPANIES) | 🥉 재무·직원·지표 카드 통째 부재 — 다른 회사 덕에 `is_loaded=True` 라 "공시 데이터 없음"만 찍힘 |
| 4 | `generator/data/krx_sector.csv` 1행 (STOCK_CD 키) | 🥈 상장사가 히트맵 "비상장" 칸에 — 조용한 오표기(하한 가드 ≥90 이라 1개 누락 못 잡음) |
| 5 | `db/seed/company_email_domain.sql` (선택) — 같은 그룹 기존 줄은 `IN(...)` 으로 합칠 것(SED-5) | 재직인증 자동 불가(수동 승인 폴백) |
| 6 | `generator/data/combinations.json` (선택) — /vs/ 조합 원할 때만 | 조합 페이지 없음(정상) |

**테스트 핀 갱신 6곳**: SD-3(`test_seed_counts.py` 102) · SI-8(`test_seed_integrity.py` 102) ·
SM-1(`test_seed_idempotency.py` 102) · SD-4(복지 총행 1553+N) · FN-1(`test_corp_load.py`
101/100 매핑 수) · (금융사면) FINANCIAL_7. slug 는 `directory.test.js` 가 자동 전수 검증
(신규 eng 는 기존 102와 정규화 후 충돌 검사 — 빌드 게이트 FR-59 가 최종 차단).

**적재·배포 순서**: `load.py` → `dart_finance --corp` → `dart_employ --corp` →
`release.sh`(재생성·IndexNow 자동·API 재시작) → STATE 카운트 갱신.

## 4. 웨이브 운영 (1웨이브 = 10~12개사, 예상 소요 반나절)

```
[W-0] 실사 프로브 12~15사 (경량 에이전트 — 공식 복지 소스·robots·접근성만)   ~2만 tok/사
[W-1] 수집 Opus 5 병렬 (배치 1 계약 그대로, 단 신규 회사용: 자기등록 INSERT
      신규 작성 + 앵커 없음 + LOGO/유형/업종 결정 포함)                    ~9만 tok/사
[W-2] 검증 Fable 5 (2~3사/에이전트) + 횡단 감사 Opus 1                     ~6만 tok/사
      ⚠ Fable 세션 한도 — 동시 4개 이상 투입 금지(429 실발현 이력)
[W-3] 등록 데이터: corp_code 매칭(사람 검수 게이트) · krx_sector · 별칭 ·
      이메일 도메인 · 금융사 세트
[W-4] 핀 갱신 → 게이트 → PR → CI → 머지
[W-5] 적재(load + dart --corp) → release.sh → 라이브 검증 → STATE
```

비용: 웨이브당 약 **150만~200만 토큰** + DART API(무료). 48개사 = 웨이브 4~5회.

## 5. 공개(SEO) 게이트 — 보류 결정과의 정합

2026-08-29 결정: 레버 D 보류, "A~C(lastmod 정직·IndexNow) 후 4주 지표 재검토" → **재검토
시점 ≈ 2026-09-26**. 두 갈래:

- **옵션 G1 (권장)**: 웨이브 1(10~12사)을 **관찰 실험으로 즉시 공개** — 네이버는 색인이
  작동하므로 유입 이득이 즉시 발생하고, 신규 페이지의 구글 크롤·색인 반응(IndexNow 경유)이
  곧 "확장이 크롤 예산을 악화시키는가"의 실측 데이터가 된다. 웨이브 2부터는 그 지표로 결정.
  판단 지표: GSC 색인 수·크롤 통계(진짜 Googlebot 로그) · 신규 페이지 색인 소요일 ·
  기존 페이지 색인 수 변화(잠식 여부).
- **옵션 G2 (보수)**: 09-26 재검토까지 W-0~W-4(수집·검증·PR)만 진행하고 적재·공개(W-5)를
  멈춘다. 준비는 끝나 있으니 게이트가 열리면 즉시 웨이브 소화.

어느 쪽이든 **웨이브 간 간격 ≥1주** — lastmod 정직성 유지(한꺼번에 수백 페이지 갱신은
2026-08-29 작업이 없애려던 바로 그 신호 오염이다).

## 7. 함정 (이 계획 고유)

- **`load.py --fresh` 금지 유지** — 회사 로스터가 바뀌는 시점엔 TCOMPARE_LOG TRUNCATE
  필요(#15)지만, 멱등 재적용(기본)은 COMP_ID 를 보존하므로 로그·게시글·인증이 안전하다.
  신규 회사는 INSERT IGNORE 로 뒤에 붙는다(재배정 없음).
- REF 번들 선형 증가(현재 607KB/102사 → 150사 ≈ 890KB) — 부팅 페이로드 예산. 200사
  근처에서 slug 만 실은 경량 번들 분리 검토(후속, 지금은 아님).
- DART `hm_url` 오염(실측 2/10) — 실사 프로브에 도메인 생존 검증 포함.
- 사명 변경 감지 — corp_code 매칭 때 DART 개황 정식명과 대조(LIG·엔씨 전례),
  표시명 바꾸면 옛 이름은 반드시 별칭에.
- 신규 회사 이메일 도메인은 **@rejected 목록·SED-5(그룹 병합) 확인 후** 추가.
